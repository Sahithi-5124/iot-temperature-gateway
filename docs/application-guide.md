# C IoT Gateway Application Guide

## 1. Overview and Architecture

The IoT Gateway Application is a lightweight, portable daemon implemented in C (ISO C11). It is designed specifically for resource-constrained, embedded Linux environments generated by Buildroot.

The application executes an autonomous acquisition-processing-logging-publishing loop:

```
+-----------------------------------------------------------------------+
|                       IoT Gateway Main Daemon                         |
|                                                                       |
|  +--------------------+        +--------------------+                 |
|  |   Sensor Module    | -----> |  Processor Module  |                 |
|  | (Deterministic or  |        |  (Threshold Check  |                 |
|  |  Realistic Sim)    |        |   & Classification)|                 |
|  +--------------------+        +--------------------+                 |
|           |                               |                           |
|           v                               v                           |
|  +--------------------+        +--------------------+                 |
|  |    Logger Module   |        |    Alert Module    |                 |
|  |   (CSV + fsync)    |        |   (Status Filter)  |                 |
|  +--------------------+        +--------------------+                 |
|           |                               |                           |
|           +---------------+---------------+                           |
|                           v                                           |
|                +--------------------+                                 |
|                |    MQTT Module     |                                 |
|                | (QoS 1, Nonblock,  |                                 |
|                |  Auto-Reconnect)   |                                 |
|                +--------------------+                                 |
+-----------------------------------------------------------------------+
```

### Key Architectural Characteristics
- **Single Process / Event Thread:** Minimal memory footprint (Virtual size ~84 MB, Resident Set Size ~6.6 MB with shared libraries loaded).
- **Graceful Lifecycle Management:** Traps both `SIGINT` and `SIGTERM` to perform full resource cleanup, socket teardown, and file sync before exiting with status `0`.
- **Immediate Logging:** Configures `setvbuf(stdout, NULL, _IOLBF, 0)` and `setvbuf(stderr, NULL, _IONBF, 0)` so redirected system logs appear immediately without block-buffering delays.
- **Strict Data Integrity:** Calls `fsync(fileno(fp))` on CSV records to guarantee data durability onto physical or virtual disk blocks.

## 2. Sensor Simulation & Input Validation

The system is strictly software-based; there is no physical hardware attached. All temperature samples are generated using software simulation and explicitly stamped with the source tag `SIMULATED`.

### 2.1 Simulation Modes

The sensor module ([sensor.c](file:///c:/Users/vivobook/Downloads/iot-2/application/src/sensor/sensor.c)) supports two operational modes controlled via the `IOT_SENSOR_MODE` environment variable:

1. **Deterministic Mode (`deterministic` - default):**
   - Sequentially cycles through fixed temperature values: `25.0°C -> 30.0°C -> 36.0°C -> 42.0°C`.
   - Designed for predictable automated testing, threshold boundary verification, and reproducible CI/CD checks.
   - Triggers all three alert levels systematically (`NORMAL`, `NORMAL`, `WARNING`, `CRITICAL`).

2. **Realistic Mode (`realistic`):**
   - Emulates real physical environment dynamics using a bounded random-walk algorithm.
   - Temperature starts at a nominal ambient value (25.0°C).
   - Each tick modifies temperature by a bounded delta: \(\Delta T \in [-1.0^\circ\text{C}, +1.0^\circ\text{C}]\).
   - Strictly clamped within the operating range `[20.0°C, 42.0°C]`.

### 2.2 Input Validation Rules

Before any temperature value is admitted into the processing pipeline, [sensor_validate()](file:///c:/Users/vivobook/Downloads/iot-2/application/src/sensor/sensor.c) applies strict validation rules:

| Condition | Check Mechanism | Result Code | Action |
|---|---|---|---|
| NaN Value | `isnan(reading->temperature)` | `SENSOR_ERR_INVALID` | Discarded, error logged |
| Infinity | `isinf(reading->temperature)` | `SENSOR_ERR_INVALID` | Discarded, error logged |
| Below Operating Limit | `reading->temperature < -40.0` | `SENSOR_ERR_OUT_OF_RANGE` | Discarded, error logged |
| Above Operating Limit | `reading->temperature > 85.0` | `SENSOR_ERR_OUT_OF_RANGE` | Discarded, error logged |
| Valid Reading | `-40.0 <= T <= 85.0` | `SENSOR_OK` | Accepted for processing |

## 3. Processing and Threshold Policy

The processor module ([processor.c](file:///c:/Users/vivobook/Downloads/iot-2/application/src/processing/processor.c)) evaluates validated readings against configured operational thresholds.

### Threshold Rules

```
     NORMAL                     WARNING                     CRITICAL
[ -40.0°C ...... 34.99°C ] [ 35.0°C ...... 39.99°C ] [ 40.0°C ...... 85.0°C ]
```

- **NORMAL (`ALERT_NORMAL`):** Temperature \(< 35.0^\circ\text{C}\). System nominal. Logged to CSV; published to `iot/temperature/readings`.
- **WARNING (`ALERT_WARNING`):** Temperature \(35.0^\circ\text{C} \le T < 40.0^\circ\text{C}\). Elevated condition. Logged to CSV; published to `iot/temperature/readings` and `iot/temperature/alerts`.
- **CRITICAL (`ALERT_CRITICAL`):** Temperature \(T \ge 40.0^\circ\text{C}\). Dangerously high temperature. Logged to CSV; published to `iot/temperature/readings` and `iot/temperature/alerts`.

## 4. Local CSV Logging & Persistence

The logger module ([logger.c](file:///c:/Users/vivobook/Downloads/iot-2/application/src/logging/logger.c)) maintains an append-only CSV audit log.

### CSV Schema

```csv
timestamp,temperature_c,source,status,alert_level
2026-11-22T09:47:32Z,25.00,SIMULATED,VALID,NORMAL
2026-11-22T09:47:34Z,30.00,SIMULATED,VALID,NORMAL
2026-11-22T09:47:36Z,36.00,SIMULATED,VALID,WARNING
2026-11-22T09:47:38Z,42.00,SIMULATED,VALID,CRITICAL
```

### Persistence and Durability Mechanism
1. **Header Detection:** If the file does not exist or has 0 bytes, the standard CSV header is written first.
2. **Standard Append:** Every entry is appended with ISO 8601 UTC timestamps.
3. **Flushing & Fsync:** After every record, the logger invokes `fflush(fp)` followed by `fsync(fileno(fp))` to ensure Linux page cache writes are committed directly to disk blocks.
4. **Persistent Path:** In the Buildroot runtime environment, the log file path is configured to `/root/temperature_log.csv` located on the root filesystem partition (`/dev/vda`), ensuring persistence across VM reboots (unlike `/var/log` or `/tmp` which reside on volatile `tmpfs`).

## 5. MQTT Networking & Outage Handling

The MQTT module ([mqtt.c](file:///c:/Users/vivobook/Downloads/iot-2/application/src/mqtt/mqtt.c)) provides reliable telemetry publication via Eclipse Mosquitto's `libmosquitto`.

### 5.1 Connection Lifecycle
- **Non-blocking Connect:** Uses `mosquitto_connect_async()` so that gateway startup is never blocked by a slow or unavailable network broker.
- **Background Event Loop:** Uses `mosquitto_loop_start()` to run a background networking thread handling ping packets, acks, and socket reconnects.
- **State Tracking:** Maintains an atomic status variable `is_connected` updated via `on_connect` and `on_disconnect` callbacks.

### 5.2 Outage Resilience & Exponential Backoff
When the broker connection is lost:
1. The `on_disconnect` callback marks `is_connected = false`.
2. The gateway daemon continues local acquisition, processing, and CSV logging without interruption.
3. A background reconnect routine initiates retries with exponential backoff:
   - Initial retry: 2 seconds
   - Successive retries: 4s, 8s, 16s, up to a maximum cap of 30 seconds.
4. Once connection is restored, `is_connected = true` and telemetry transmission resumes automatically.

*Note on Delivery Guarantees:* Published telemetry uses QoS 1 (At least once). Messages dropped while disconnected are discarded in memory to prevent unbounded memory growth on constrained embedded targets; local persistence is preserved in the CSV log.

## 6. Environment Configuration Reference

The application dynamically reads configuration variables at startup:

| Environment Variable | Default Value | Buildroot VM Value | Description |
|---|---|---|---|
| `IOT_SENSOR_MODE` | `deterministic` | `deterministic` | Sensor mode (`deterministic` or `realistic`) |
| `IOT_INTERVAL_SEC` | `5` | `2` (in init script) | Sampling interval between readings in seconds |
| `IOT_LOG_FILE` | `temperature_log.csv` | `/root/temperature_log.csv` | Absolute path to CSV persistence log |
| `MQTT_BROKER_HOST` | `localhost` | `10.0.2.2` | Hostname or IP of MQTT broker (`10.0.2.2` is QEMU host) |
| `MQTT_BROKER_PORT` | `1883` | `1883` | TCP port of MQTT broker |

## 7. Compilation and Unit Testing

The application Makefile supports standalone host compilation and unit testing:

```bash
# Build the gateway executable
cd application
make

# Execute full unit test suite (sensor, processor, alert, logger, mqtt, mqtt_reconnect)
make test

# Clean all build artifacts and test binaries
make clean
```
